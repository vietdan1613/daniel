When building modern UIs with React, layout matters. A lot. In some cases, your UI needs to *measure* the size or position of an element **before** rendering it the right way. Think about dropdowns, tooltips, or popovers—they often need to know where they are on the page **before** deciding where to render.

But what happens when you can’t know the layout until *after* the DOM is painted?

That’s where layout computation—and `useLayoutEffect`—comes into play.

---

## 📐 What Is Layout Computation?

Layout computation is the process of measuring the dimensions or position of UI elements *before* displaying them correctly on the screen. For example:

* A tooltip should appear **above** or **below** the target element depending on available space.
* A modal or popover should be centered based on the viewport size.
* A list should scroll to the right item after mount.

These measurements need to happen **before** the browser paints the screen. Otherwise, you'll get what's known as **flickering**—the component is rendered incorrectly at first, then "jumps" to the correct position once the measurements are in.

---

## 🐛 What Causes UI Flickering?

Imagine you render a tooltip based on the target element’s position:

```tsx
useEffect(() => {
  const rect = ref.current?.getBoundingClientRect()
  if (!rect) return
  const { height } = rect
  setTooltipHeight(height)
}, [])
```

At first glance, this looks fine. But `useEffect` runs **after** the screen is painted. So on low-end devices or slower environments, users might briefly see the tooltip in the wrong place (say, below the element), before it repositions itself (to above).

This creates a visual flicker that affects user experience.

---

## 💊 The Fix: `useLayoutEffect`

The fix is simple: switch from `useEffect` to `useLayoutEffect`.

```tsx
useLayoutEffect(() => {
  const rect = ref.current?.getBoundingClientRect()
  if (!rect) return
  const { height } = rect
  setTooltipHeight(height)
}, [])
```

Here’s what makes `useLayoutEffect` powerful:

* It **runs synchronously** after the DOM has been updated.
* It **blocks the browser** from painting until your code runs.
* You can **safely measure layout** and apply styles **before** the user sees anything.

This small change eliminates flickering by ensuring the UI is in its final position *before* the screen updates.

---

## ⚖️ `useEffect` vs `useLayoutEffect`

| Feature             | `useEffect`                        | `useLayoutEffect`                           |
| ------------------- | ---------------------------------- | ------------------------------------------- |
| Timing              | After the paint                    | Before the paint                            |
| Use case            | Async data, logging, subscriptions | Measuring layout, synchronously reading DOM |
| Performance concern | Doesn’t block rendering            | Might delay painting                        |
| Common usage        | Most side effects                  | Rare, layout-specific effects               |

So, unless you're dealing with **layout-based** side effects, prefer `useEffect`. But when measurements and positions matter—like with tooltips—`useLayoutEffect` is your friend.

---

## 💡 A Real Example: Tooltip Positioning

In the [Epic React](https://www.epicreact.dev/workshops/advanced-react-apis/intro-to-layout-computation) workshop, there's a tooltip that sometimes flickers. Here's what happens:

1. Tooltip first renders **below** the heart icon.
2. After measuring, it realizes there's space **above**, and jumps up.
3. That *jump* causes a distracting flicker.

By switching to `useLayoutEffect`, the measurement is complete before the screen is painted, so the tooltip just appears in the right place—**no flicker**.

## ✅ Key Takeaways

* Use `useLayoutEffect` when your UI depends on DOM measurements before the browser paints.
* Avoid using it unless necessary—it blocks painting and may impact performance.
* For layout-sensitive UIs like tooltips, popovers, or modals, it's the right tool for the job.
* For all other side effects (like fetching data), stick to `useEffect`.

---

React gives us powerful hooks, and choosing the right one makes a big difference in user experience. So next time you're debugging a mysterious flicker—ask yourself:

> Should this be in `useLayoutEffect`?
