`useEffect` is a built-in hook that allows you to run some custom code
after React renders (and re-renders) your component to the DOM. It accepts a
callback function which React will call after the DOM has been updated:

A **side effect** is anything that React components shouldn’t do during rendering.

### Examples of common side effects:

* Fetching data from an API
* Subscribing to a WebSocket or external store
* Directly manipulating the DOM
* Setting a timer (`setTimeout`, `setInterval`)
* Logging to the console (sometimes considered a minor side effect)
* Updating global state or localStorage

![example](./1.png 'example')

```tsx
useEffect(() => {
	// your side-effect code here.
	// this is where you can interact with browser APIs for example
	doSomeThing()
	return function cleanup() {
		// if you need to clean up after your side-effect (like unsubscribe from an
		// event), you can do it here
		doSomeCleanup()
	}
}, [
	// this is where dependencies of your useEffect callback go
	// we'll talk about this in depth in a future exercise.
	// In this exercise, we'll just leave it as an empty array
	dep1,
	dep2,
])
```

### 🛠️ `useEffect` Example:

```jsx
import { useEffect, useState } from 'react';

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    // Side effect: fetching data from API
    fetch(`/api/users/${userId}`)
      .then(res => res.json())
      .then(data => setUser(data));
  }, [userId]); // Dependency array

  return user ? <div>{user.name}</div> : <p>Loading...</p>;
}
```

## The Scenario

Let’s say you have a search form. When a user submits a query, the app updates 
the URL’s search parameters using a custom `setGlobalSearchParams` utility — without 
triggering a full-page reload. Pretty slick!

But here’s the problem: When the user clicks the **browser back button**, the URL 
updates, but the input field doesn’t reflect the previous query.

That’s because our input is controlled by React state, and we’re not listening for 
changes triggered by browser navigation (like the back or forward button).

## Solution

The browser fires a [`popstate`](https://developer.mozilla.org/en-US/docs/Web/API/Window/popstate_event) 
event whenever the user navigates with the back or forward buttons. 
To handle this in React, we add a listener inside a `useEffect`.

### Step-by-step:

1. **Extract a helper function to get the query param**:

   ```tsx
   function getQueryParam() {
     const params = new URLSearchParams(window.location.search)
     return params.get('query') ?? ''
   }
   ```

2. **Initialize the query state lazily**:

   ```tsx
   const [query, setQuery] = useState(getQueryParam)
   ```

3. **Update query state when `popstate` fires**:

   ```tsx
   useEffect(() => {
     function handlePopState() {
       setQuery(getQueryParam())
     }

     window.addEventListener('popstate', handlePopState)

     // Clean up to avoid memory leaks
     return () => {
       window.removeEventListener('popstate', handlePopState)
     }
   }, [])
   ```

4. **Ensure that when the user clicks the back button**, the input reflects 
the correct query from the URL.

## Why Cleanup Matters

When your component mounts, it adds an event listener. If it **unmounts** but 
the listener isn’t removed, the function remains in memory, along with any 
**variables captured** in its closure. Over time, this causes a **memory leak**.

React allows you to return a cleanup function inside `useEffect` to solve this:

```tsx
useEffect(() => {
  function handleEvent() {
    // some logic
  }

  window.addEventListener('event-name', handleEvent)

  return () => {
    window.removeEventListener('event-name', handleEvent)
  }
}, [])
```

This is especially important in apps where components are dynamically mounted/unmounted 
(e.g., toggling tabs, modals, forms, etc.).

### Clean up when you...

| You use...                        | You should...                    |
| --------------------------------- | -------------------------------- |
| `addEventListener`                | `removeEventListener`            |
| `setTimeout` / `setInterval`      | `clearTimeout` / `clearInterval` |
| WebSocket/EventSource             | `close()`                        |
| Observables or data subscriptions | `unsubscribe()`                  |
| Custom event buses                | `off()` or equivalent            |
| Third-party UI instances          | `destroy()` or cleanup method    |

## 🗣️ Final Thoughts

Understanding `useEffect` and its lifecycle behavior is essential for building 
efficient React apps. Always remember:

* **Listen** for events carefully
* **Clean up** after yourself
* **Test** with toggles and memory profiling

If you're teaching others or working on a growing app, this knowledge will save 
you and your teammates from subtle bugs and performance issues down the line.
