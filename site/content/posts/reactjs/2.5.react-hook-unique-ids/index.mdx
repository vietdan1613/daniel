When building React applications, especially forms, **accessibility** and **reusability** 
are two goals that often come into conflict. A classic example of this is managing the 
`id` attributes on form elements like `<input>` and `<label>`.

If you've ever created a reusable `Field` component and found that clicking the label doesn't 
focus the input — this post is for you. Let's dive into why that happens and how React's 
`useId` hook elegantly solves it.

## The Problem: Label Doesn’t Focus Input

Imagine we have a reusable `Field` component:

```tsx
function Field({ label, name }) {
  return (
    <div>
      <label htmlFor={name}>{label}</label>
      <input id={name} name={name} />
    </div>
  )
}
```

This works — until you use the `Field` multiple times on a single page **with the same `name` prop**. 
Then, you end up with **duplicate `id`s**, which is **invalid HTML** and breaks accessibility.

> When a `<label>` has a `for` attribute pointing to a non-unique `id`, assistive technologies 
(like screen readers) can’t associate them correctly. And the browser might not focus the input 
when clicking the label.

---

## Why Not Just Use `name` as `id`?

Because it’s not guaranteed to be unique.

If you render two `<Field name="email" />` components (like for billing and shipping), both inputs will have `id="email"`, causing a collision.

Also, requiring the developer to always pass a unique `id` can be annoying and error-prone.

---

## ✅ The Solution: `useId` Hook

React 18 introduced the [`useId`](https://react.dev/reference/react/useId) hook to address this very problem.

### What is `useId`?

`useId` generates a **unique, stable identifier** that:

* Is consistent across renders.
* Works in **server-side rendering** (SSR) environments.
* Is perfect for associating labels and inputs for accessibility.

### How to Use It

```tsx
import { useId } from 'react'

function Field({ label, name }) {
  const id = useId()

  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} name={name} />
    </div>
  )
}
```

Boom — now every instance of `Field` gets its own unique `id`, solving our duplicate problem.

---

## 🧙‍♂️ But Wait, What If I Want to Provide My Own `id`?

Good question.

Sometimes, developers **do** want to specify an `id` (maybe to anchor to it with a link or for testing purposes). So we should support both:

### ✅ Final `Field` Component with Optional `id` Prop

```tsx
import { useId } from 'react'

function Field({ label, name, id: customId, ...props }) {
  const generatedId = useId()
  const id = customId ?? generatedId

  return (
    <div className="field">
      <label htmlFor={id}>{label}</label>
      <input id={id} name={name} {...props} />
    </div>
  )
}
```

### Usage Examples

```tsx
<Field label="Username" name="username" />
<Field label="Email" name="email" />
<Field label="Special Field" name="special" id="custom-id-123" />
```

* The first two get automatically generated IDs from `useId()`.
* The last one uses the developer-provided ID.

---

## Don’t Use `useId` for Keys

```tsx
// ❌ Wrong! Don't use useId() here
list.map(item => <li key={useId()}>{item}</li>)
```

`useId` is **only for DOM element associations** (like `label` ↔ `input`, or `aria-labelledby`, etc).

For list keys, always use **stable, data-derived values** like `item.id`.

---

## 🧑‍🦽 Why This Matters (Accessibility)

By properly linking `<label>` with `<input>` via the `id`/`htmlFor` attributes:

* Screen readers can announce the correct label.
* Users can click the label to focus the input — critical for keyboard/motor support.
* You avoid invalid HTML and potential runtime bugs.

> Accessibility is not optional. It’s part of responsible UI development.
